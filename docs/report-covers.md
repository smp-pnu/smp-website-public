# 리포트 표지 준비와 복구

현재는 GitHub Actions가 원본 PDF 첫 페이지를 렌더링하고, 목록용 720px WebP와 상세용 최대 2048px WebP를 준비합니다. 이미지는 Cloudflare 정적 파일로 배포하며 메타데이터는 D1에 저장합니다. Vercel Blob 설정이나 방문자 요청 중 PDF 변환은 사용하지 않습니다.

## 평상시

Drive에 PDF를 올리고 Notion 리포트에 파일 링크·공개·게시일을 설정합니다. 서명된 변경 알림/보조 동기화 → 게시 대기열 → GitHub 게시 작업 → 이미지 배포 → 최신 공개 여부 확인 순서로 진행합니다. 처음 게시할 때 준비 시간이 필요하며 정확한 완료 시간은 보장하지 않습니다. [실행 상태와 수동 복구](operations.md)를 참고하세요.

제목·본문 변경이나 공개 해제 후 재공개 때도 같은 PDF이면 기존 표지를 재사용합니다. 게시 작업은 PDF 바이트의 SHA-256을 비교하므로 원본 다운로드는 발생할 수 있지만 내용이 같으면 이미지 렌더링·새 정적 배포를 생략합니다. 공개 해제는 보관된 표지 기록을 유지하고, 실제 Notion 항목 삭제·CMS 이탈은 기록을 제거합니다.

동일 Drive 파일 ID에 PDF 버전만 바꾼 경우 Notion 변경 알림은 발생하지 않습니다. GitHub 게시 워크플로의 `refresh-report`와 해당 Notion 페이지 ID를 사용하세요. 글 삭제/재생성이나 제목의 임의 변경은 필요하지 않습니다. 원문이 바뀌면 새 표지, 같으면 기존 표지가 유지됩니다.

## 저장과 안전장치

- `/report-covers/<페이지 ID>/<SHA-256>.webp`는 내용별 정적 이미지입니다. 다음 배포 전 현재 사용하는 모든 이미지를 확보하고 해시를 검사합니다. 캐시가 사라졌다는 이유로 기존 표지를 누락한 채 배포하지 않습니다.
- `free_report_covers`는 재공개 때 사용할 검증된 PDF 해시/표지 주소를 보관하고 `free_content`는 현재 공개 자료를 나타냅니다. 둘은 의도적으로 분리돼 있습니다.
- 새 표지는 게시 완료 시점의 최신 소속·공개·수정 버전이 맞을 때만 연결합니다. 한 글 실패로 원본 PDF나 다른 글을 삭제하지 않습니다.
- 실패는 최대 5회 자동 시도 후 대기합니다. 원인을 고친 뒤 관리 워크플로 `retry-failed`로 해당 글만 재시도합니다.
- 공개 이미지 주소나 이미 내려받은 파일은 Notion 공개 해제만으로 회수되지 않습니다. 민감한 내용을 표지·공지 이미지에 올리지 않습니다.

## 코드

`free/jobs/prepare.ts`: PDF 해시·WebP 준비. `free/jobs/publish.ts`: 대기열·이미지 보전·배포. `free/server/jobs.ts`: 작업 임대와 최종 공개 검증. `free/server/publisher.ts`: 제한된 자동 실행 요청. `free/jobs/maintenance.ts`: 상태/재시도/수정 PDF 확인. 초기 웹훅 연결은 [Cloudflare 연결 안내](free-webhook.md)를 사용합니다.

## 전체 페이지 읽기 준비

공개 리포트는 게시 작업에서 첫 3페이지와 전체 페이지 읽기 파일을 미리 생성합니다. 발행 연도와 목록 순서에 관계없이 적용합니다. PDF 내용이 같으면 표지를 재사용하고, 전체 읽기 파일도 캐시가 유효한 동안 재사용합니다. 내용이 바뀌거나 캐시가 소실되면 필요한 파일을 다시 준비합니다. 변환 실패는 완료로 표시하지 않고 기존 게시 재시도와 운영 상태 안내를 사용합니다.

방문자는 먼저 준비된 1~3페이지를 봅니다. 전체 읽기 파일을 한 번 받으면 페이지 이동과 확대에 같은 이미지를 재사용하며 원본 PDF를 자동으로 중복 다운로드하지 않습니다. 압축된 이미지를 보관하고 현재 페이지와 인접 페이지만 화면에 디코딩합니다. 텍스트 선택·원문 링크를 사용할 때만 별도 버튼으로 PDF 원문 모드를 엽니다. 원본 다운로드는 Drive 원본을 유지합니다.

읽기 파일은 공개 여부·본문 버전·원본 크기와 수정 시각을 확인하는 API에서만 제공합니다. 브라우저도 SHA-256·크기·페이지 수를 확인합니다. 데이터 절약·2G 연결, 파일 손상이나 읽기 오류에서는 PDF 원문 뷰어로 전환합니다. 느린 연결에서는 전체 파일을 받는 시간이 필요하며, 모든 방문자에게 즉시 넘김이 가능하다고 보장하지 않습니다.

## 기존 자료 일괄 준비

GitHub 게시 작업의 `prepare-library`는 최대 200건을 순차 처리하는 수동 작업입니다. 별도 200건/일 제한이 있고, 평소 게시 50건/일과 누락 자료 보완 20건/일은 유지합니다. Notion 공통 호출 예산과 재시도 대기 시간은 동일하게 적용합니다. 변경되지 않은 본문을 재사용하고 Notion의 기업 정보 자동 입력을 생략하므로 불필요한 호출과 속성 변경을 줄입니다. 이 작업 중 기존 사이트는 계속 제공되며 다른 게시 작업은 대기할 수 있습니다.

## 읽기 파일의 안전 한도

- 전체 읽기 파일: 최대 120페이지·파일당 24MiB, 합계 2GiB. 오래된 자료라는 이유로 제거하지 않습니다.
- 선택적 최적화 PDF: 원문당 최대 32MiB를 1MiB 조각으로 저장하며, 최신 최대 32개·합계 256MiB만 유지합니다. 이 사본이 없으면 Drive 원문을 사용합니다.
- 빌드: 읽기 파일·PDF 조각 합계 1,544개, 전체 정적 파일 18,000개 이하를 검사합니다. 완성된 읽기 파일의 복구 실패나 합계 용량 초과 시 이전 배포를 유지합니다.
- 변환은 공개 저장소의 표준 GitHub Actions 실행기에서 처리합니다. 방문자 요청 중 PDF 이미지 변환이나 유료 이미지 변환 서비스는 사용하지 않습니다. GitHub 캐시 유료 확장이나 Cloudflare 유료 요금제로 자동 전환하지 않습니다.

위 수치는 서비스 업체의 요금 기준과 별개인 운영용 안전 한도입니다. 한도 초과 파일은 기존 PDF 경로로 읽을 수 있으며, 관리자가 운영 상태에서 해당 자료를 확인해야 합니다. 자료가 증가해 합계 한도에 가까워지면 무료 서비스 제한과 실제 사용량을 다시 검토한 후 조정합니다.
