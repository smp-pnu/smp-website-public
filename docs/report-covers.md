# 리포트 표지 준비와 복구

현재는 GitHub Actions가 원본 PDF 첫 페이지를 렌더링하고, 목록용 720px WebP와 상세용 최대 2048px WebP를 준비합니다. 이미지는 Cloudflare 정적 파일로 배포하며 메타데이터는 D1에 저장합니다. Vercel Blob 설정이나 방문자 요청 중 PDF 변환은 사용하지 않습니다.

## 평상시

Drive에 PDF를 올리고 Notion 리포트에 파일 링크·공개·게시일을 설정합니다. 서명된 변경 알림/보조 동기화 → 게시 대기열 → GitHub 게시 작업 → 이미지 배포 → 최신 공개 여부 확인 순서로 진행합니다. 처음 게시할 때 준비 시간이 필요하며 정확한 완료 시간은 보장하지 않습니다. [실행 상태와 수동 복구](operations.md)를 참고하세요.

제목·본문 변경이나 공개 해제 후 재공개 때도 같은 PDF이면 기존 표지를 재사용합니다. 게시 작업은 PDF 바이트의 SHA-256을 비교하므로 원본 다운로드는 발생할 수 있지만 내용이 같으면 이미지 렌더링·새 정적 배포를 생략합니다. 공개 해제는 보관된 표지 기록을 유지하고, 실제 Notion 항목 삭제·CMS 이탈은 기록을 제거합니다.

동일 Drive 파일 ID에 PDF 버전만 바꾼 경우 Notion 변경 알림은 발생하지 않습니다. GitHub 게시 워크플로의 `refresh-report`와 해당 Notion 페이지 ID를 사용하세요. 글 삭제/재생성이나 제목의 임의 변경은 필요하지 않습니다. 원문이 바뀌면 새 표지, 같으면 기존 표지가 유지됩니다.

## 저장과 안전장치

- `/report-covers/<페이지 ID>/<SHA-256>.webp`는 내용별 정적 이미지입니다. 다음 배포 전 현재 사용하는 모든 이미지를 확보하고 해시를 검사합니다. 캐시가 사라졌다는 이유로 기존 표지를 누락한 채 배포하지 않습니다.
- `free_report_covers`는 재공개 때 사용할 검증된 PDF 해시/표지 주소를 보관하고 `free_content`는 현재 공개 자료를 나타냅니다. 둘은 의도적으로 분리돼 있습니다.
- 새 표지는 게시 완료 시점의 최신 소속·공개·수정 버전이 맞을 때만 연결합니다. 한 글 실패로 원본 PDF나 다른 글을 삭제하지 않습니다.
- 실패는 최대 5회 자동 시도 후 대기합니다. 원인을 고친 뒤 관리 워크플로 `retry-failed`로 해당 글만 재시도합니다.
- 공개 이미지 주소나 이미 내려받은 파일은 Notion 공개 해제만으로 회수되지 않습니다. 민감한 내용을 표지·공지 이미지에 올리지 않습니다.

## 코드

`free/jobs/prepare.ts`: PDF 해시·WebP 준비. `free/jobs/publish.ts`: 대기열·이미지 보전·배포. `free/server/jobs.ts`: 작업 임대와 최종 공개 검증. `free/server/publisher.ts`: 제한된 자동 실행 요청. `free/jobs/maintenance.ts`: 상태/재시도/수정 PDF 확인. 초기 웹훅 연결은 [Cloudflare 연결 안내](free-webhook.md)를 사용합니다.

## 읽기 시작 속도

게시할 때 앞 3페이지를 최대 2048px WebP로 함께 만듭니다. 방문자는 목록 표지를 즉시 재사용하고, 상세 공개 상태를 확인한 뒤 준비된 1~3페이지를 넘겨볼 수 있습니다. PDF가 준비되면 선택한 페이지에서 이어집니다. 새로 연 페이지와 캐시에 없는 이미지는 네트워크 속도의 영향을 받습니다.

게시 작업은 pikepdf/qpdf로 화질을 낮추지 않고 페이지 색인을 모아 둔 열람용 PDF도 준비합니다. 원본 다운로드는 Drive 원본을 유지합니다. 열람용 사본은 1 MiB 조각으로 나눠 원문당 32 MiB 이하, 최신 자료 최대 32개·합계 512 MiB까지만 배포하고, 없는 사본·상한 초과·원본 변경 시 기존 Drive 경로로 전환합니다. 직접 정적 주소로 PDF에 접근할 수 없으며 기존 공개 검증 API를 거칩니다. 같은 Drive ID의 파일 교체를 감지하기 위해 원본 크기·수정 시각을 최대 5분마다 확인합니다.

기존 자료는 게시 작업이 없을 때 하루 최대 20건씩 준비합니다. 기존 하루 50건 준비 한도 안에서 처리하므로 평소 게시를 위한 여유를 남깁니다. 서명·암호화 PDF는 최적화하지 않으며, 새 준비가 실패하면 기존 자료를 유지합니다. Python 변환 도구는 방문자 서버가 아닌 GitHub 게시 작업에서만 실행됩니다.

조각형 사본은 전체 PDF 캐시를 먼저 채우지 않고 요청 구간부터 전송합니다. PDF.js도 준비된 사본에만 범위 전송을 사용해 전체 파일과 범위를 중복 다운로드하지 않습니다. 공개 확인과 원본 신선도 검증은 유지하며, 초기 요청 취소 시 남은 조각 전송도 멈춥니다. 기존 단일 파일 사본은 갱신 전까지 호환 경로를 사용합니다. 파일 수는 전체 18,000개·PDF 조각 544개 이하로 빌드에서 검사합니다.

첫 페이지가 실제 사용하는 구간도 게시 시 기록합니다. 뷰어는 이를 최대 8 MiB·동시 요청 4개 이내로 먼저 읽고 같은 구간 요청은 공유합니다. 모든 요청은 현재 공개 상태를 확인하며 준비된 PDF 해시에 고정됩니다. 사본이 없어졌거나 바뀌면 기존 URL 로딩으로 자동 복귀합니다.

첫 화면 표시 후 앞 3페이지를 순차 준비하고, 크기가 검증된 조각형 사본(최대 32 MiB)은 남은 구간을 뒤에서 채웁니다. 연속 구간은 최대 4 MiB씩 묶어 API 호출을 줄이며 이미 받은 바이트는 PDF.js가 재사용합니다. 데이터 절약·2G 연결에서는 전체 선로딩을 생략하고, 숨긴 탭은 다시 열 때 시작합니다. 앞 3장 이후에는 남은 바이트 수신과 나머지 페이지 렌더링을 겹쳐 진행하며, PDF.js의 같은 바이트 캐시를 재사용합니다. 일반 페이지는 빠른 무손실 PNG로 보관하고, PNG가 1.5 MiB를 넘는 사진 위주 페이지는 기존 품질 94 WebP와 비교해 작은 쪽을 보관합니다. 해상도와 확대 품질은 유지합니다. 버전이 주소에 포함된 PDF.js·글꼴·CMap 파일은 브라우저에서 1년 재사용합니다. 준비 완료 후에는 PDF를 다시 그리지 않고 이미지를 교체합니다. 압축 화면 캐시는 모바일 32 MiB·데스크톱 64 MiB·최대 120장이며, 상한 도달 시 읽는 페이지를 우선합니다. 화면에는 최대 3개 이미지와 현재 페이지의 텍스트·링크 계층만 유지하고 새 이미지가 디코딩된 뒤 교체합니다. 확대 시 기존 이미지를 먼저 보여주고 고해상도 PDF 캔버스를 덧그립니다. 탭을 숨기면 추가 페이지 렌더링을 멈추고, 문서를 닫으면 작업·임시 이미지 URL을 정리합니다. 서버 저장·게시 작업·일일 사용량 상한은 그대로이며, 전체 파일을 미리 받으므로 첫 페이지만 읽고 나갈 때의 전송량은 증가합니다.


### 게시 시 전체 페이지 준비

최신 열람용 사본에는 최대 60페이지·16 MiB의 고화질 WebP 페이지 묶음을 함께 준비합니다. PDF와 묶음을 합쳐 기존 512 MiB·544개 파일 상한을 지키며 최신 32개 자료 중 공간이 있는 것만 배포합니다. 생성은 기존 게시 작업에서 최대 60초 동안 실행하고, 실패·상한 초과 시 원문과 앞 3장 미리보기는 유지합니다. 기존 자료 보완은 하루 20건, 전체 게시 작업 하루 50건 범위 안에서 수행합니다. 시도 완료 표시로 지원되지 않는 문서를 반복 생성하지 않습니다.

묶음은 공개 여부·본문 버전·원본 크기와 수정 시각·PDF 해시를 검증하는 기존 API에서만 제공합니다. 브라우저는 SHA-256과 크기·페이지 개수를 검증한 뒤 한 번 받은 묶음을 페이지 이동·창 크기 변경에 재사용합니다. 원본 PDF의 앞 구간부터 읽는 동작과 첫 3장 미리보기는 유지하며, 나머지 PDF 바이트는 뒤에서 받습니다. 화면에 맞춤에서는 준비된 이미지를 표시하고 텍스트 선택·링크·확대는 PDF 원문을 사용합니다. 실패한 묶음은 한 번만 시도한 후 기존 브라우저 렌더링으로 전환합니다. 문서를 닫으면 요청과 임시 이미지 URL을 정리합니다. 문서당 이미지 묶음 요청 1회와 최대 16 MiB 전송이 추가되므로 느린 연결의 속도까지 보장하지는 않습니다. 별도 유료 저장소나 서비스는 사용하지 않습니다.
