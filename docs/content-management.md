# 일상 관리와 복구

> 2026-10-27 관리자 CMS 전환 이후 현재 사용법과 운영 기준은 [관리자 CMS 운영](admin-cms.md)을 따릅니다. 이 문서의 Notion 동기화·시험 운영 설명은 이전 구조의 기록입니다.

현재 학회 Notion의 관리 홈에서 **SMP 게시 운영 현황**과 **SMP 모집 안내 관리**를 엽니다. 실제 연결 식별자는 비공개 운영 설정에 보관합니다.

## 게시 현황

- 원문을 수정한 뒤 공개합니다. 운영 현황의 `준비 중 → 게시 완료`를 확인하고 홈페이지 링크를 열어 최종 확인합니다.
- `확인 필요`이면 안내에 나온 원본 파일·공유 권한 등을 먼저 고친 뒤 GitHub Actions의 `retry-failed`를 해당 원문 ID로 실행합니다.
- 공개를 해제한 기존 글은 `게시 제외`로 표시합니다. 운영 현황은 원문 목록과 분리되어 있고 여기서 제목·상태를 바꾸어도 원문은 바뀌지 않습니다.
- 현황 갱신은 실행당 최대 8행, 하루 최대 240행입니다. 변경 없는 행은 쓰지 않습니다. 초기 등록·대량 수정은 여러 실행으로 나뉩니다. Notion의 기존 게시 작업 호출 상한 안에서 동작합니다.
- 목록과 상세·PDF에는 기존 공개 검증이 그대로 적용됩니다. 상태 행은 마지막 게시 작업이 확인한 결과이고 실시간 모니터링을 대신하지 않습니다.

## 모집 안내

`현재 홈페이지 모집 안내` 행의 속성만 수정합니다. 행 추가·삭제나 본문의 메모는 홈페이지 모집 내용을 바꾸지 않습니다.

1. 기수·일정 표시·대상·요건·인원·활동 일정·장소·기간·회비·전형 안내를 작성합니다.
2. 접수를 시작하려면 `모집 중`, `일정 확정`, 접수 시작과 종료, HTTPS 지원 링크가 모두 필요합니다.
3. 날짜만 지정한 시작일은 한국 시간 00:00, 종료일은 23:59:59입니다. 종료 후 지원 링크를 열 수 없도록 브라우저에서도 확인합니다.
4. 잘못된 값은 마지막 정상 설정을 유지하며 운영 현황에 오류를 표시합니다. 수정 후 다음 게시 작업에서 다시 확인합니다.

설정은 게시 실행에서 한 번 읽어 정적 화면으로 배포합니다. 방문자가 많아져도 모집 안내 때문에 Notion API 호출이 늘어나지 않습니다. 예약 실행은 외부 서비스 상황에 따라 지연될 수 있습니다.

## Drive 백업

기존 학회 Apps Script에 `scripts/drive-cleanup/Backup.gs`를 추가합니다. 기존 Drive·Notion 권한을 사용하며 웹 앱의 공개 주소는 추가하지 않습니다. `MEMBERS_DATA_SOURCE_ID`, 선택적으로 `RECRUITMENT_DATA_SOURCE_ID`, `BACKUP_STATUS_PAGE_ID`를 Script Properties에 설정한 후 `enableBackups`를 한 번 실행합니다.

- 백업 폴더는 학회 Drive 최상위에 있는 **SMP 웹사이트 · 비공개 복구 백업**입니다. 폴더를 공유하면 백업을 중단합니다. 운영 자료의 공개 폴더 안으로 옮기지 않습니다.
- 매주 리포트·공지·회원·모집 DB의 스키마와 전체 목록·속성(비공개 초안 포함)을 JSON으로 보관합니다. 삭제된 자료를 복구할 때 이전 스냅샷을 사용합니다.
- 변경된 원문은 본문과 연결 파일 목록을 보관합니다. 리포트 원본 폴더 안의 Drive 파일은 복사하고, 지원하는 Notion 업로드 파일은 만료 전 별도 보관합니다. 외부 웹사이트의 링크는 JSON에만 남습니다. 표지는 PDF에서 재생성할 수 있습니다.
- 처음에는 전체 원문을 나누어 처리합니다. 이후 수정일이 같은 글·같은 버전의 PDF는 재복사하지 않습니다. 원본과 별개의 복사본이라 원본을 휴지통으로 옮겨도 백업은 남습니다.
- 시간당 한 번, 실행당 최대 24건·150초, 하루 최대 256건·본문 조회 300회·실행 15분·파일 100MB입니다. 전체 목록 조회와 상태 알림은 별도로 소량 발생합니다. 백업 누적 2GB 또는 Drive 사용량 85%에서 멈춥니다. 한도를 우회하거나 유료 전환하지 않습니다.
- 완료한 원문 수·대기 수·확인 필요 상태를 Notion 운영 현황의 `비공개 복구 백업`에서 봅니다. 백업이 다 끝나지 않은 동안 `준비 중`으로 표시됩니다.
- `verifyBackups`는 체크포인트 무결성, 복구 JSON 형식, 표본 파일 존재·비공개 여부를 확인합니다. 파일이 실제로 열리는지도 학기마다 표본 확인합니다.

## 복구 절차

1. 사고 직전 `catalog-종류-날짜.json`에서 해당 행과 속성을 찾습니다. `page-...json`에는 본문과 `files`의 원본↔백업 파일 ID 매핑이 있습니다. `backup-index`는 복구 대상 파일 목록이고 이전 체크포인트도 남깁니다.
2. 기존 페이지가 Notion 휴지통에 있으면 먼저 복원합니다. 없으면 해당 DB에 새 비공개 행을 만든 뒤 속성·본문을 복구합니다. 원문의 `공개` 값이 true여도 검토 전에는 공개하지 않습니다.
3. 복사 PDF·사진을 정상 운영 폴더에 다시 복사하고 필요한 파일만 공유한 뒤 새 링크로 바꿉니다. 백업 폴더 자체를 공개하지 않습니다. URL이 만료된 Notion 파일은 `files` 매핑의 사본으로 다시 업로드합니다.
4. 글 하나를 먼저 확인하고 공개해 본문·표지·PDF를 검증합니다. 전체 데이터를 바로 덮어쓰지 않습니다.
5. Cloudflare D1 장애는 별도로 공급자의 Time Travel과 Notion 재동기화를 사용합니다. Drive 백업에는 API 키, Worker Secrets, D1 임시 작업 큐가 없습니다.

같은 Google 계정의 백업은 계정 상실까지 대비하지 못합니다. 학기 인수인계 때 백업 폴더와 원본을 담당자 보관 장치에도 내보내고, 계정 복구 수단을 인계합니다. 누적 보관량 상한에 도달하면 기존 백업을 별도로 내보낸 뒤 불필요한 버전을 직접 정리합니다.
