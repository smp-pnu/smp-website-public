# 리포트 게시 순서 운영 및 인수인계

## 평상시 사용

1. 학회 Notion의 `SMP 웹사이트 관리 → 리포트 게시 순서`를 엽니다.
2. 리포트 링크 줄 왼쪽의 `⋮⋮`를 잡아 위아래로 옮깁니다. 번호는 Notion이 자동으로 매깁니다. 같은 들여쓰기 깊이를 유지하고 한 줄에 한 리포트를 둡니다.
3. 보통 1~2분 후 웹사이트 `/research`를 새로고침합니다. Notion 알림은 보통 1분 이내, 최대 약 5분 안에 전달되며 서버의 순서 캐시는 60초입니다. [Notion 이벤트 전달](https://developers.notion.com/reference/webhooks-events-delivery).
4. 새 글은 기존 리포트 DB에서 작성·공개하고, 이 목록의 끝에서 Enter로 새 번호 줄을 만든 뒤 `@`로 리포트 페이지를 선택합니다. 리포트의 Notion 페이지 링크를 붙여 넣어도 됩니다. 제목만 입력하면 연결되지 않습니다. Drive 링크는 계속 리포트 DB의 `외부 링크`에 넣습니다.

리포트 공개 여부는 항상 원래 DB의 공개 체크·게시일·제목으로 판단합니다. 순서 페이지에 비공개 글 링크가 있어도 공개되지 않습니다. 목록에 링크가 없는 공개 글은 뒤에 붙고, 중복 링크는 첫 번째 위치만 반영됩니다. 링크를 지우면 글은 뒤로 이동합니다. 게시를 중단하려면 DB에서 **공개 체크를 해제**하세요.

기존 `표시 순서` 숫자 속성은 링크가 없는 글의 보조 정렬용으로 남아 있습니다. 매번 수정하지 않아도 됩니다. DB 표의 행 드래그 순서나 숫자 속성은 자동 변경하지 않습니다. 웹사이트의 순서는 이 별도 페이지에서 관리합니다.

## 최초 연결

1. 기존 Notion 관리 페이지 아래에 일반 페이지를 만들고, 최상위 번호 목록에 리포트 페이지 멘션/링크를 하나씩 넣습니다. 기존 `SMP Website` 읽기 전용 연결이 하위 페이지에 접근 가능한지 확인합니다. 쓰기 권한은 필요 없습니다.
2. 페이지 주소의 ID를 Vercel Production 환경변수 `NOTION_REPORT_ORDER_PAGE_ID`에 넣고 배포합니다. 실제 ID와 비밀값은 공개 저장소에 기록하지 않습니다.
3. 기존 Notion 웹훅이 `/api/notion/webhook`의 `page.content_updated`를 구독 중인지 확인합니다. 표지 자동화의 Blob 저장소, 서명 검증 토큰, `CRON_SECRET`을 재사용합니다. 새 저장소나 유료 서비스가 필요하지 않습니다.
4. 서버의 `CRON_SECRET`을 Bearer 인증 헤더에 넣어 `POST /api/admin/research-order`를 한 번 호출합니다. 응답의 `configured: true`, 링크 개수와 저장 시각을 확인합니다. 비밀값은 URL·Notion·로그에 넣지 않습니다. 이 관리자 호출은 초기 설정이나 장애 복구에만 사용합니다.
5. Notion에서 실제 링크 블록을 드래그하고 자동 웹훅만으로 사이트 순서가 바뀌는지 확인합니다. 일상 편집에는 재배포나 관리자 API 호출이 필요 없습니다.

## 구현과 호출량

- 방문자 요청은 기존 Notion 공개 목록을 한 번 조회합니다(100개 초과 시 페이지당 추가 조회). 순서 페이지는 조회하지 않습니다. 현재 공개 목록을 얻은 뒤 저장된 순서를 적용하므로 공개 해제가 지연되지 않습니다.
- 순서 스냅샷은 동일 서버에서 60초 동안 공유하고 동시 읽기를 합칩니다. 서버가 새로 시작하거나 캐시가 만료되면 작은 Blob 하나를 읽습니다. 카드마다 순서를 조회하지 않습니다.
- 순서 페이지의 변경 알림을 받으면 페이지 상태와 최상위 블록을 읽고, 순서가 실제 바뀐 경우에만 Blob을 갱신합니다. 순서만 옮겨도 PDF나 표지를 다시 만들지 않습니다.
- 공개 Blob 스냅샷에는 임의 페이지 ID의 SHA-256 해시와 저장 시각만 담습니다. 원본 ID, 비공개 제목, 본문, Drive 주소, 토큰은 저장하지 않습니다. 공개/예약 상태는 스냅샷이 아닌 현재 DB로 판단합니다.
- 최대 250개 고유 링크, 최상위 1,000블록을 지원합니다. 한도를 넘기거나 읽기에 실패하면 이전 저장본을 보존합니다. 조건부 쓰기가 충돌하면 Notion의 최신 순서를 다시 읽어 재시도하므로 늦은 알림이 최신 순서를 덮어쓰지 않습니다.
- 기존 일일 표지 동기화 작업이 순서도 재확인합니다. 별도의 Cron을 추가하지 않습니다. 저장소 장애 시 같은 서버에 남은 마지막 순서를 사용하고, 없으면 기존 숫자·날짜 정렬로 표시합니다. 콘텐츠 목록 자체를 숨기지는 않습니다.

## 인수인계와 복구

다음 담당자에게 순서 페이지와 리포트 DB 위치를 알려주고 드래그·새 링크 추가·공개 해제를 직접 해보게 합니다. 페이지 제목은 바꿔도 되지만, **삭제하거나 복제본으로 교체하면 페이지 ID도 달라지므로 환경변수 변경과 재배포가 필요**합니다. 읽기 연결과 웹훅을 해제하지 마세요.

6분 이상 바뀌지 않으면 링크가 리포트의 Notion 페이지인지, 최상위 블록인지, Notion 연결이 접근 가능한지 확인합니다. 다음으로 웹훅 전달 결과와 Vercel 함수 로그, Blob 사용 한도를 확인합니다. 관리자 재동기화는 인증된 POST만 사용합니다. 페이지가 휴지통에 들어갔거나 권한이 사라지면 마지막 저장 순서를 유지하므로 페이지 복원/연결 복구 후 다시 동기화합니다.
